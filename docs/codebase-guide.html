Darb receipt intelligence

How the full codebase works

This system takes a receipt or tax invoice, finds the card transactions it is allowed to inspect, ranks the plausible matches, and either attaches the document safely or asks a finance reviewer to decide.

1
The payment already existsWe match proof documents to existing transactions. We do not process payments.
2
The score is explainableAmount, merchant, card, and date contribute visible evidence.

Safety beats confidenceA 100% candidate still goes to review when another candidate is equally good.

End-to-end journey

Nine stages, one document

Select a stage for its detailed explanation. Each stage shows how it works, why it exists, and the files that own it.

01

Receive the document

The HTTP boundary turns provider events into a common ingestion input.

Output: file bytes + sender
How it works

The email route decodes Base64 attachments. The WhatsApp route walks Meta's nested payload, loads the media ID through MediaStore, normalizes the phone, and sends both sources to ingestDocument().

Why this design

Provider-specific formats stop at the route. The rest of the system receives one consistent shape, so matching does not know or care whether a receipt came from email or WhatsApp.

email/route.tswhatsapp/route.tsmedia/types.ts
02

Validate and authenticate

Untrusted network input is rejected before it reaches domain logic.

Output: typed payload
How it works

The route keeps the raw body for HMAC-SHA256 verification, parses JSON once, then calls Zod safeParse(). Invalid emails, missing arrays, or non-image WhatsApp messages return HTTP 400.

Why this design

TypeScript disappears at runtime. Zod protects the real API boundary, while timingSafeEqual prevents a subtle signature comparison leak. The same schema also generates TypeScript types.

webhooks/schemas.tswebhooks/signature.ts
03

Detect redelivery and duplicate receipts

The same evidence must not create multiple records or claims.

Output: new or existing document
How it works

Ingestion checks provider ID, tenant-scoped SHA-256 content hash, and a semantic fingerprint built from authorization, invoice, or QR identity. Database unique constraints resolve concurrent redeliveries.

Why this design

A provider ID catches normal retries, a byte hash catches renamed files, and semantic identity catches scans or re-encodings. Tenant scoping prevents one client's receipt from suppressing another's.

document-ingestion.tsschema.prisma
04

Extract structured receipt fields

Unstructured document bytes become reliable matching evidence.

Output: ExtractedDocument
How it works

DocumentExtractor exposes one async extract() contract. The assessment uses a deterministic hash-backed mock. ZATCA TLV QR fields fill missing seller, VAT, date, and total values without overwriting visible OCR.

Why this design

The interface makes real OCR replaceable while tests remain offline. Per-field confidence lets weak OCR reduce its own scoring influence. Extraction failures are persisted instead of crashing the webhook.

extraction/types.tsmock-extractor.tszatca-qr.ts
05

Load only plausible, authorized transactions

Candidate selection is both an access-control rule and a performance boundary.

Output: candidate block
How it works

Email sender maps through ClientEmail to clientId. WhatsApp sender maps to driverPhone. A printed date adds a ±30-day database filter. Frequency values are calculated only inside this safe block.

Why this design

Scoring should never choose a transaction the sender is not allowed to see. Pre-filtering keeps tenancy outside the pure matcher and avoids comparing every receipt with the entire ledger.

document-ingestion.tsschema.prisma
06

Score, rank, and handle ambiguity

The matcher produces evidence, not a mysterious yes/no answer.

Output: ranked candidates
How it works

scoreTransaction() combines amount, merchant, card, and Riyadh-local date. Missing signals are re-normalized. OCR reliability reduces weights. Strong identifier matches boost confidence; reliable contradictions penalize it.

Why this design

Finance needs to understand decisions. A pure deterministic function is easy to test, audit, and tune. An absolute threshold plus a runner-up gap handles the “two candidates at 100%” case correctly.

transaction-matcher.tsmatcher-edge-matrix.test.ts
07

Persist one consistent lifecycle result

Documents and relationships move together or not at all.

Output: terminal state
How it works

A Prisma transaction writes the document status and DocumentMatch rows. Safe winners become AUTO_CONFIRMED; review cases save up to five CANDIDATE rows; low scores become UNMATCHED; extraction errors become FAILED.

Why this design

Transactions prevent half-written decisions. Raw SQL adds a partial unique index so a transaction can own only one CONFIRMED or AUTO_CONFIRMED document, even under races.

schema.prismainitial migration
08

Let a human resolve uncertainty

The reviewer sees both sides of the comparison and finalizes the relationship.

Output: confirmed or rejected
How it works

The server page queries pending documents and candidate transactions. Match and Reject call Zod-validated server actions. Confirmation rejects siblings; rejecting the last candidate moves the document to UNMATCHED.

Why this design

The score never replaces judgment in ambiguous cases. Side-by-side fields, signal chips, conflicts, and tie labels show exactly what is being compared. Race-safe updates prevent stale reviewer clicks.

review/page.tsxdecision-buttons.tsxreview-service.ts
09

Explain, rematch, and evaluate

Supporting services improve operations without changing deterministic scoring.

Output: learning signals
How it works

Explanations are generated only on click and cached by evidence hash. UNMATCHED documents can be rescored after new transactions arrive. Human-confirmed rows feed ranking, precision, coverage, and calibration metrics.

Why this design

LLM prose remains presentation-only. Rematching handles out-of-order events. Evaluation creates a responsible path from hand-chosen heuristics to thresholds supported by real reviewer labels.

Matching logic

A high score is necessary, not sufficient

The engine first ranks candidates, then applies separate safety gates before automation.

Core signal weights

Available weights are re-normalized when a receipt genuinely lacks a field.

Three values, three meanings

Similarity measures available-field agreement. Evidence coverage measures how much was present. Decision confidence discounts similarity by missing evidence and drives the safety thresholds; it is still not a calibrated probability.

Every auto-match gate must pass

Failing one gate sends the document to review, even when available-field similarity is 100%.

✓
Lead ≥ 12%Not tied with runner-up
✓
Evidence ≥ 70%Not a sparse perfect score
✓

✓

✓

MATCHED

Safe winner was confirmed automatically or by a reviewer.

NEEDS_REVIEW

Plausible candidates exist, but automation gates did not all pass.

UNMATCHED

No candidate reached the review threshold.

FAILED

Extraction or pipeline work could not produce matchable evidence.

After human labels exist

Measure safety before increasing automation

Reviewer-confirmed decisions become ground truth. Automatic matches never grade the same rules that created them.

Highest risk

False positives

An automatically attached transaction was wrong. Track the count, rate, merchant/source slices, and every corrected example.

Review cost

False negatives

A correct top candidate was unnecessarily withheld from automation. This measures safe work the engine missed.

Ranking

Top-1 + Recall@K

Measure whether the correct transaction ranked first and whether it appeared anywhere in the top 3 or 5 candidates.

Automation

Precision, recall, coverage

Precision protects money; recall and coverage show how much correct work is automated; review rate shows operator load.

Trust

Calibration

Brier score and expected calibration error show whether a displayed score agrees with observed correctness.

Operations

Latency, failures, queue age

Track p50/p95/p99 latency, terminal states by reason code, extraction failures, dedupe rate, and time to human decision.

!
Optimize in the right order

First protect automatic-match precision and false-positive rate. Only then lower review workload. Always tune on one period and report results on a separate held-out period.

Why this architecture

Key engineering choices

The implementation optimizes for correctness, explainability, clean assessment setup, and a realistic path to production.

Purity

Scoping outside matching

Tenant authorization stays in ingestion. The matcher remains a pure function that can be tested with plain objects.

Money safety

Integer halalas

Amounts never use floating-point currency math. SAR 250.00 is stored as 25,000 halalas.

Ambiguity

Threshold + score gap

A strong candidate is not enough; it must also be clearly stronger than the runner-up.

Reliability

Database constraints

Unique indexes—not optimistic application checks—are the final defense against duplicates and conflicting confirmations.

Replaceability

OCR and media interfaces

Fixtures keep the assessment deterministic, while interfaces define where real provider implementations plug in.

AI boundary

LLM explains, never decides

The deterministic matcher owns the outcome. Optional generated prose only translates stored evidence for a reviewer.

Honest boundaries

Assessment-ready, not production-complete

The architecture exposes the right seams, but these integrations deliberately remain outside the take-home scope.

Mocked

Real OCR and Meta media

Current implementations recognize repository fixtures. Production classes would call OCR and WhatsApp APIs behind the existing interfaces.

Not wired

Transaction ingestion trigger

rematchUnmatched() exists, but no real card-feed endpoint calls it when a transaction arrives.

Future

Queues, auth, and document preview

Production should add authenticated reviewers, durable background jobs, blob storage, and original PDF/image preview.
